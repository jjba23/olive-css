* Set up a checkout
:PROPERTIES:
:CUSTOM_ID: setup
:END:

Guile 3.0 is the only requirement to build and run the CLI.  The full
environment - Veritas, Maak, the documentation tools and the exact Guile the
project is tested with - comes from the manifest:

#+begin_src shell
git clone https://github.com/jjba23/olive-css.git
cd olive-css
guix shell -m manifest.scm -- guile --version
#+end_src

Nix users get the same toolchain from ~nix develop~; the flake exports the
package and a development shell.

* Tasks
:PROPERTIES:
:CUSTOM_ID: tasks
:END:

[[https://codeberg.org/jjba23/maak][Maak]] is the task runner.  Run ~maak~ with no task to list them.

| Task               | What it does                                                       |
|--------------------+--------------------------------------------------------------------|
| ~maak build~       | regenerate every stylesheet in =resources/css/= via the CLI         |
| ~maak tree-shake~  | prune the sample page's build into =public/olive.min.css=           |
| ~maak test~        | run the Veritas unit suite                                         |
| ~maak fmt~         | format every Scheme file with ~guix style~                          |
| ~maak compile~     | byte-compile =src/= and =tools/=                                    |
| ~maak docs~        | generate the API documentation under =doc/=                         |
| ~maak deploy~      | build, generate and publish the API documentation                  |
| ~maak release~     | commit, tag, push and publish a GitHub release                     |
| ~maak hot-reload~  | rebuild whenever a Scheme or CSS file changes                      |
| ~maak agents~      | regenerate =AGENTS.md= from the pinned skills                      |
| ~maak container-build~, ~maak container-run~ | the container image                    |

_AGENTS.md is generated; edit the ~agents~ task in =maak.scm=, never the file._

* Project layout
:PROPERTIES:
:CUSTOM_ID: layout
:END:

| Path                      | What lives there                                              |
|---------------------------+---------------------------------------------------------------|
| =src/olive-css/=          | the library: generator, DSL, sizes, tree-shaker, builds, CLI  |
| =src/olive-css/decl/=     | one module per utility family                                 |
| =bin/olive-css=           | the launcher around ~(olive-css cli)~                          |
| =test/veritas/unit/=      | the Veritas suites                                            |
| =tools/release.scm=       | the release tool, loaded with =-L .=                           |
| =resources/css/=          | the generated stylesheets this repository ships               |
| =docs/=                   | the documentation, one topic per file                         |
| =packaging/=              | Debian, openSUSE and Arch recipes                             |

A new utility family gets a module under =decl/=, an export from
~(olive-css main)~ if the complete build should include it, and a test.  A new
shipped stylesheet gets an entry in ~build-specs~.

* Tests
:PROPERTIES:
:CUSTOM_ID: tests
:END:

#+begin_src shell
guix shell -m manifest.scm -- maak test
#+end_src

The suite uses [[https://codeberg.org/jjba23/veritas][Veritas]] and covers the tree-shaker (escaping, scanning,
pruning rules, the no-leakage invariant), the build registry and CLI, and the
release helpers.  Keep it green before a commit; a test names the behaviour it
protects, and a new branch or loop gets one.

* Documentation
:PROPERTIES:
:CUSTOM_ID: docs
:END:

The guide is Org, one =*= heading per page, =**= for sections, =#+TITLE= and
=#+EMAIL= at the top, =CUSTOM_ID= on anything linked from elsewhere and
=file:= links between pages.  The [[file:index.org][index]] lists every page.  A
user-visible change updates the page that owns the feature and the changelog's
Unreleased section; the release tool turns that section into the release notes.

The Scheme API is generated by ~maak docs~ into =doc/api-dist= and published at
https://jointhefreeworld.org/api-docs/olive-css/API.html.

* Cutting a release
:PROPERTIES:
:CUSTOM_ID: release
:END:

A release is one command.  First bump ~olive-css-version~ in
=src/olive-css/cli.scm=, write the changes into the *Unreleased* section of
=CHANGELOG.org=, commit them, and make sure the tree is clean and on =trunk=:

#+begin_src shell
guix shell -m manifest.scm -- maak release
#+end_src

The task then:

1. moves the Unreleased entries under =* vX.Y.Z - YYYY-MM-DD= and leaves an
   empty Unreleased stub;
2. writes the version into =src/olive-css/cli.scm=, =default.nix=, the openSUSE
   spec, the Arch recipe and the Debian changelog;
3. commits =chore: Release vX.Y.Z=, creates the annotated tag =vX.Y.Z= and
   pushes both =trunk= and the tag;
4. publishes a GitHub release whose notes are the changelog section just cut;
5. downloads the new tag's archive, refreshes the Arch checksum, and pushes that
   as =build: Update the Arch checksum for vX.Y.Z=.

It refuses to run on a dirty tree, off =trunk=, or when the tag already exists.
Those checks are why there is no half-finished release to repair.  If the
checksum step cannot reach the archive it prints a warning and leaves the
recipe for you to update by hand; the release itself is already published.

* Packaging
:PROPERTIES:
:CUSTOM_ID: packaging
:END:

The recipes under =packaging/= build the same sources and install the library,
the launcher, the licence and the guide.  They are pinned to the release tag by
the release task, which also fills in the Arch checksum.  Build one with:

#+begin_src shell
# Debian / Ubuntu
cp -r packaging/debian . && dpkg-buildpackage -us -uc -b

# openSUSE
osc build packaging/opensuse/olive-css.spec

# Arch
cd packaging/arch && makepkg -si
#+end_src

The container is built with ~podman build -t olive-css .~ and starts the CLI:
~podman run --rm -it olive-css --help~.

* Continuous integration
:PROPERTIES:
:CUSTOM_ID: ci
:END:

Pushes to =trunk= run =maak-test= and =maak-deploy= through the
[[https://byggsteg.jointhefreeworld.org][Byggsteg]] reusable workflow.  That
publishes the API documentation once the suite passes, on the same pinned
environment you get from the manifest.  The workflow lives in
=.github/workflows/ci.yml= and has no project steps of its own to maintain.

It needs the repository secrets =BYGGSTEG_EMAIL= and =BYGGSTEG_PASSWORD=
(Settings → Secrets and variables → Actions).  GitHub rejects the call before
any step runs while either is missing, so a red run with a secrets annotation
means the account details are not configured, not that the suite failed.
